## N226 · Evidence-safe Atlas graph edits via MCP

### Safety and scope
This release adds one command-only registered resource, `atlas_graph_edits`, with four owner-bound, idempotent, auditable operations. It does not need a provider API key: ChatGPT/Claude proposes edits using the existing authenticated MCP tool and the owner reviews consequential changes. The existing `concepts` resource and its commands are unchanged.

### Operations
- `change_level`: `target.id` (concept UUID), `expectedVersion`, `patch:{level}`. Enforces strict parent < child level progression: cluster, galaxy, system, planet, moon.
- `delete_empty`: `target.id`, `expectedVersion`, `patch:{}`. Rejects any child, link, checkpoint, note, diagnostic, practice topic or retained Atlas evidence. Does not permit silent graph deletions.
- `reclassify_link`: `target.id` is source concept, `expectedVersion`, `patch:{to_id,from_kind,to_kind}`. Updates one row transactionally; the existing cycle guard validates any new prerequisite edge.
- `link_batch`: `patch:{links:[{from_id,to_id,kind,from_version,to_version},...]}`, 1–50 links and no top-level target. Validates all endpoint versions before inserting any, uses the existing cycle guard, journals one owner transaction, and bumps each distinct source once.

All operations have an owner-bound command receipt; a retry of the exact operationId/payload returns the saved receipt, while a changed retry conflicts. No direct DML by an unauthenticated browser is added.

### Merge safety
The existing `concepts.merge` rewires only a subset of concept references. A new protective BEFORE DELETE trigger refuses deleting a source concept if it still carries attempt tags, instruction events, legacy evidence, assumptions, recheck decisions, typed links, aliases, practice-bank rows, rechecks, skill family references or item tags. A facts-bearing duplicate should be preserved as a separate row and connected using an approved alias; a source with no such history remains eligible for the existing audited merge. This avoids destructive data loss without weakening the append-only evidence rules. Account deletion cascades remain supported through an owner-account-deletion guard.

### X blockers
X4 is made lossless by refusing unsafe physical merges and offering aliases for identities that must retain history. X7 gains level edits and truly empty deletion. X8 gains atomic link type changes. X9 gains one version-checked batch transaction without removing optimistic concurrency. X1 and X6 are handled by N225, X5 intentionally uses aliases. X2 uses the connected scheduled AI task; X3 uses the suggested tags read and explicit confirmation (never invented evidence). Real unattended task availability must still be acceptance-tested after deployment.

### Release gate
Apply only through the repository's additive reviewed Supabase pipeline after full SQL parity, owner isolation, Undo, and smoke tests. No existing user graph is automatically changed. Do not treat a code PR or a scheduled-task definition as proof that the release has been deployed and qualified.
