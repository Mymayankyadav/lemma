## Bug #1816 — Preserve saved notes on uncertain card creation

`LiveAdapter.createNote` no longer compensates a failed card-insert acknowledgement by deleting its already-created parent note. The parent is visible to other clients, so even a rejected insertion does not authorize cascading away another client's work.

On a returned insert error or a thrown transport failure, the adapter performs one read filtered by the authenticated owner and exact note ID. If every expected card ordinal is present, it returns the original note number without another write. If the read fails or any expected ordinal is absent, it preserves the saved data and reports the original error. Successful creation keeps its existing two-write path. Auth-generation checks before writes and around reconciliation reject retired receipts, including sign-out and same-owner re-login, without swallowing the auth error.

Eleven caller-level tests inject the transport boundary, including a commit followed by another client's grade before acknowledgement loss, complete versus incomplete cloze sets, failed reconciliation, a definite insert rejection and the ordinary successful path. Seven tests fail on unchanged main; all eleven pass after this patch. The fixture models persisted rows and cascading deletion, not a live database. No production account or data was used.

Limits: this is not atomic/idempotent note creation. An actual rejected card insert can leave an incomplete note rather than deleting it unsafely, and a failed readback still reports uncertainty. Parent-note acknowledgement loss and safe replay remain separate issue #1805. Existing RLS and note/card foreign-key behavior are assumed; no schema, privilege, deployment or CI changes are included.
