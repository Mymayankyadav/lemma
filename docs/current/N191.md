## N191 Durable evidence, owner-scoped receipts and calendar snapshots

The November 20 P3 foundation journals the canonical evidence and calendar writers and exposes pinned reads for a signed-in owner or a verified connector. The shared release capability starts disabled.

### Accepted evidence

`evidence_revisions` captures records and voids in the transaction that modifies `evidence`, `attempts`, `attempt_tags` or `instruction_events`. It uses the relational owner, project, source identity and event linkage. Updates from correction, supersession, physical deletion and undo produce revisions. When a fact leaves a project, its old project receives a void in the same transaction as the surviving owner record. A converted Atlas attempt retains its `source_evidence_id`, allowing consumers to identify the same observation across representations.

`lemma_evidence_snapshot(p_project_id, p_as_of, p_watermark, p_after, p_limit)` derives the owner from the authenticated session. Its inclusive cutoff applies to occurrence time, source report time and server acceptance time. A PostgreSQL MVCC watermark excludes transactions still open when the read occurred. Use the returned `asOf`, `watermark` and opaque decimal `nextAfter` on subsequent pages. A decision should save the server-issued cutoff and watermark with its outcome. The read returns immutable events for the existing `replayEvidence` implementation to fold by source and lineage. IDs cross the JSON boundary as strings.

Pre-existing facts first become known at installation. Later imports can reconcile one owner and source in bounded pages through `lemma_seed_evidence_page`. Repeating a page preserves the original knowledge timestamp and revision. The database does not reconstruct knowledge from before the first capture.

### Command and receipt authority

The existing `study` connector accepts resource `session_progress` and operation `save`. Supply a stable operation UUID, the target session ID, its `progress_version` and a canonical progress patch. The connector derives its owner from the verified credential. In one transaction the command checks ownership, locks the existing owner-wide operation key, validates the current session version, calls the original `save_progress` writer and records the resulting IDs, version, event count and journal action. Legacy updates and undo advance the same session version. Exact delivery returns the saved result even after later edits. A changed request or a collision with another resource produces a conflict. Users can keep using the original save flow.

P1, P3 and P6 share `lemma_trusted_receipt_begin` and `lemma_trusted_receipt_finish`. Each outer command must verify current owner, actor, target and any grant generation before returning a receipt. Both helpers use `command_receipts(user_id, operation_id)`. The private receipt contains a SHA-256 digest over normalized JSONB, with stable object order, significant array order and normalized numeric scale. An explicit private legacy marker ensures old commands reject UUID collisions. The public response contains neither the digest nor the submitted content.

New writes require the separately reviewed owner migration that removes effective browser table and column mutation grants and installs the server-writer marker. Previously written receipts keep their historical retry semantics. New commands treat rows without verified provenance as collisions. The production writer also requires `lemma_plan_released()`. `usePlanRelease` scopes the browser's capability cache to its auth generation. Replays of authorized, previously accepted writes can still recover their original acknowledgement after a release hold.

### Calendar and service reads

`lemma_calendar_snapshot(p_horizon_end, p_as_of, p_watermark)` reads the owner's historical input projections. Planned one-off blocks retain their original ID and version. Weekly blocks accept an inclusive local date range, weekdays, and start and end wall times with optional fold choices in the block's IANA zone. An occurrence is identified by the original series, zone and civil date. Append a revision to `calendar_occurrence_changes` to move or cancel it. The highest revision wins. Conflicting latest revisions, unresolved DST folds and nonexistent times hold the snapshot, including when an occurrence moves across the original query horizon.

The response returns fixed intervals with their buffers and project-specific study windows with their project IDs. In the absence of an explicit study window it can use the owner's stored daily planning window and weekday capacity, including per-date overrides. Explicit zero yields an empty array. Missing information yields null. Daily caps accompany the dated windows for the decision consumer. The reader retains absolute instants and does not change assignments or external calendars.

`lemma_planning_snapshot_mcp(p_owner, p_kind, p_args)` is a service-role-only counterpart. Pass the verified connector owner and either `evidence` or `calendar`. The inner reader applies the same signed-owner filters and the wrapper restores its temporary claims on return. The historical tables and occurrence exceptions participate in the existing owner export and account deletion mechanisms. The migrated-evidence freeze recognizes the protected purge transaction by its owner, backend PID and transaction ID. The purge retries both PostgreSQL foreign-key and RESTRICT errors while it removes dependent rows.

### Acceptance and rollout

Run `node tests/mcp/sql/n191-receipt-compat.mjs` for the complete migration chain and owner/service exercises. Point `NOTIF_TEST_DATABASE_URL` to the isolated local PostgreSQL 17 control database to run separate-backend duplicate and rollback races and verify that an in-flight accepted fact stays out of a pinned historical replay after commit. The fixture creates and removes its own database. It tests the protected receipt and release states only inside that fixture.

The regression suite covers canonical correction and undo, native Atlas attempt/tag/instruction writes, trusted/legacy UUID conflicts, stale versions, atomic rollback, paged reads, DST parity, scoped service reads, export and account purge. Existing pure tests remain in `tests/unit/evidence` and `tests/unit/calendar/fixed-occurrences.test.ts`. Deployment of the owner cutover, independent PR review and the single release decision remain separate gates.
