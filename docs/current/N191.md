## N191 Candidate evidence replay and fixed calendar normalization

`src/lib/evidence/replay.ts` is a pure, unwired candidate for the Nov 20 plan §6 and P3. The reference application contract supplies the occurrence/reporting cutoff and latest revision semantics; the reference recovery contract supplies owner scope and known time. The port applies all three clocks independently, includes the exact cutoff, compares offset-bearing instants at submillisecond precision, and never consults a device clock. The immutable event ID is owner-scoped; a source and lineage ID identify revisions. Equivalent JSON copies deduplicate, conflicting IDs/revisions fail, and a visible void retains its history without contributing active evidence. A future-known correction or conflict does not alter an earlier replay. The caller must still derive the owner/source and assign the trusted known time.

`src/lib/calendar/fixedOccurrences.ts` normalizes a candidate snapshot of weekly fixed commitments. It preserves series/original IANA zone/original local date identity after moves, chooses the latest revision regardless of delivery order, deduplicates equal revisions, and blocks competing latest revisions. Overnight spans use the next local date. The strict resolver reuses the existing civil-time offset calculation, but requires an explicit fold choice and refuses spring gaps unless the occurrence is moved to valid times or cancelled. A blocked snapshot exposes no partial set to a scheduling consumer. The function takes bounded original-date ranges, has no device clock or persistence, and does not change the existing study-day fallback rules.

### Shared owner command receipts (P1 / P3 / P6)

Reuse `public.command_receipts`, whose primary key is `(user_id, operation_id)`; the UUID namespace is owner-wide, not scoped to a resource. The [task](../../supabase/migrations/20261106180000_v6_task_command.sql) and [review-run](../../supabase/migrations/20261111020000_review_runs_command.sql) commands take the same owner/UUID transaction lock, compare the immutable JSONB `_request`, and remove private request data before returning their saved outcome. This contract does not change those RPCs.

1. **Authenticate before replay.** Derive the owner and actor from the server-validated login or bounded grant, never the request body. Check current actor capability, grant/claim generation where applicable, and authority for the requested or stored target before exposing its receipt. Privileged reads and links must still filter on the derived owner. Actor/provenance/freshness metadata supplied by the client is not authority.
2. **Freeze one intent.** Allocate one UUID when the user submits one logical command and retain the exact normalized envelope in that owner's pending state before transport. A timeout, lost acknowledgement, app restart or failed readback retries that same UUID and envelope. Include schema version, command resource and operation, target, expected version and typed patch in request identity. Define defaults and omission vs. null per command; normalized JSON objects ignore key order, arrays preserve order. Do not change a retry's timestamp/default or regenerate a UUID simply because the outcome is unknown. A deliberate edit after resolution is a new operation. Reset/fence pending work at account changes.
3. **Replay before mutable version checks.** After authenticating, serialize on the owner/UUID using the existing advisory lock convention. Look up the receipt with that key, not a resource-filtered key. If the resource and immutable request match, return only the originally saved DTO (`operationId`, status, stable changed IDs/versions, action number and any scoped result); no fresh side effect, readback-derived receipt, or version rejection. If the resource, operation, or request identity differs, return conflict, with no original payload/IDs leaked. A legacy receipt lacking comparable request identity is a conflict, not permission to act again. A current authorization failure still wins over replay. Use the existing normalized JSONB comparison for bounded non-secret envelopes; when persisting raw body would retain sensitive or large content, use a versioned digest of an explicitly canonical encoding in the same private receipt, not a second store. Never include secrets, content or raw digests in logs/ordinary responses.
4. **Apply exactly once.** On a miss, validate command shape and linked records, lock target rows, and check every relevant expected version inside the write transaction. New rows use absent/zero expected version if the command explicitly declares that convention; linking to an existing parent still checks its owner and any relevant parent version. Rejected stale inputs make no domain change and do not reserve a successful receipt. Append authoritative domain facts and their journal action plus the saved receipt in that transaction. A rollback leaves neither; acknowledgement follows commit. Undo is a distinct journalled operation; a retry of the old UUID returns the original outcome, never reapplies an undone mutation.
5. **Separate transaction truth from replay time.** Preserve occurred and reported clocks as facts; the server assigns the accepted known time in the successful transaction, not from the client, and publishes no uncommitted event. Capture a server as-of cutoff and a coherent committed source snapshot/version for a decision; keep both with the decision receipt. `command_receipts.created_at` defaults to transaction start, not commit, and must not substitute for event visibility or justify retroactive inclusion. If identical historical cuts must be reproducible across transactions, pin an owner-scoped committed ledger watermark/snapshot identity as well as the clock. Replaying a write returns its stored receipt; it never runs a solver at the current clock.
6. **Make the trust boundary real before enabling consumers.** The table's [repository baseline](../../supabase/migrations/20261105141000_v6_study.sql) grants authenticated owner CRUD under RLS. Owner isolation alone does not make stored receipts server-authored or immutable. Verify the actual privileges, inventory existing invoker writers, and design/test compatible server-only write authority before trusting rows for new P1/P3/P6 flows. No privilege change is made here. Add local migration tests for anonymous/authenticated/service roles and different owners; prove one action/result under concurrency, exact lost-ack replay, cross-resource/payload conflict, stale version and rollback. Avoid treating receipt DTOs or logs as raw content export; reconcile owner export/purge through the existing registry.

**P1 first path + first card:** The current path draft adapter does a project insert and picks a numbered slug on collision; the hook's in-memory “created” state is not durable after a lost acknowledgement. The preferred implementation is one owner-bound command that creates/links the project and initial card/note atomically and records both durable IDs/versions for the same UUID; use existing validators and journal conventions. Source-file uploads remain separate owner-scoped operations. Open P1 decision: whether the flow includes sources or content that cannot fit the command transaction, and if so whether product wants a separate upload phase or a resumable multi-step design. A partial result must never be inferred from a slug collision or treated as a successful compound receipt. P1's N189 quick-capture diff does not implement this command.

**P3 durable evidence:** Map occurrence, report and known clocks, validate event/source/lineage and owner-linked session/item records, and persist the event plus command receipt atomically. Command UUID and immutable evidence event ID are separate identities: a different command still cannot accept different content under an existing event ID or create a duplicate fact. Do not set a new known time for an exact duplicate; validate origin and corrections/voids against trusted state. This doc freezes the boundary, not adapter/schema details or production behavior.

### Evidence ingress reference transaction

`src/lib/evidence/ingress.ts` is an unwired, dependency-injected reference for one server transaction, not a browser API or a receipt store. It authorizes a linked target before exact operation replay, snapshots the allowlisted request, and serializes owner/operation and event/source-lineage identities separately. Owner, source and known time are supplied by the trusted transaction; neither duplicate delivery nor an exact event submitted with a new operation ID advances the original known time. Different owner/target authorization, changed request identity, event/revision conflicts, stale versions and an aborted receipt write all fail without returning a new successful result. P6 can reuse the ordering (authorize → operation lock → replay/conflict → domain/version lock → write and receipt → commit); its generation checks and narrower responses remain domain-specific. The fake storage proves the algorithm, not Postgres locking or RLS.

**Migration-compatible receipt authority:** Keep the existing table and owner-wide key. Audit actual grants and inventory direct readers, command writers, exports and purge jobs first. Convert dependent invoker writers behind owner-bound hardened RPCs with the same request/response, journal and retry semantics, and verify those old consumers against local migration fixtures before removing authenticated direct mutation. At the reviewed ACL cutover, permit receipt mutation only through trusted writers, keep any authorized read/export behavior deliberately scoped, and version new server-authored receipt identity. Rows predating the cutover do not acquire trusted provenance retroactively; keep legacy retries on their compatible path, and treat legacy key collisions in new commands as conflicts. No new consumer should rely on a client-writable receipt even if results have a verification mark: deleting the row could defeat retries. No schema/ACL change is included; the Owner must review cutover scope, legacy handling, and rollout before new commands use durable receipts in production.

### Integration remaining

- N169 evidence already has owner-scoped read access and session/project/checkpoint/concept relationships, `occurred_at`, creation time, and mutable void/supersede markers. N181 applies parallel correction semantics to Atlas attempts. The current facts reader consumes present non-void rows, not a historical prefix. Preserve its production behavior. Add trusted report/known semantics without treating historical backfill timestamps as fact; validate the event linkage under the owner and prove correction/undo and historical replay are consistent before changing callers.
- Reuse the existing `command_receipts` mechanism and the shared contract above. The task command already serializes owner/operation ID and distinguishes changed-payload retries. Evidence integration still needs one transaction covering immutable input identity, linked-record validation, accepted event and durable receipt, plus concurrent duplicate and one-lost-ack tests. The pure function is not a receipt store or authorization layer.
- The existing Calendar contract is one-off, versioned blocks, and `_shared/adaptive/calendar.ts` ranks or clips concrete slots. The candidate recurrence port still needs a trusted series/revision source (including moves across the query's original-date bounds), absolute horizon slicing, buffers and overlap handling, and a scheduler boundary that turns a blocked snapshot into a hold. No persistence, recurrence adapter or user-facing calendar changes are included here.
- Still pending: integration parity fixtures, trusted model/settings/commitment inputs, cross-owner database/service and concurrent receipt tests, export/deletion coverage, and rollout review.

Focused regression cases are in `tests/unit/evidence/replay.test.ts`, `tests/unit/evidence/ingress.test.ts` and `tests/unit/calendar/fixed-occurrences.test.ts`. No consumer, migration, dependency, flag, or production setting was changed.
