## Bug #1209 — prevent changed Atlas create after uncertain acknowledgement

The initial #1201 fix correctly replayed a pending owner Atlas create for an identical payload, but keyed its pending map by the create payload itself. Changing the name, blurb, subject, or parent after a lost HTTP acknowledgement generated a different map key and a fresh command instead of blocking an unresolved create. Two concepts could be committed when the owner intended to retry one.

The live owner Atlas adapter now reserves a single **owner-specific create slot** while the initial command has an uncertain outcome. The exact same create payload replays its original operation ID; a different create payload conflicts until the first intent resolves authoritatively. Existing concept mutations retain their per-target isolation, and any successful or definite failed create frees the slot. No SQL, migration, new dependency or production function changes.

A focused regression simulates the first command committing with two HTTP acknowledgements lost, then attempts a renamed create without sending another RPC, retries the original command with exactly the same envelope and one saved receipt, and demonstrates that a new independent create is permitted after successful reconciliation.
