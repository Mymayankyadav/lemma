## Bug #1201 — preserve Atlas graph mutation identity after lost acknowledgements

The N105.2 live Atlas adapter previously built a fresh `operationId` whenever a user clicked Save again, even when the first `concepts_command` committed but its two HTTP acknowledgements were lost. The SQL receipt guard could not associate the subsequent click with that action, causing duplicate-command conflicts and misleading failure messages for create, link and merge.

The live adapter now keeps one complete, immutable command envelope in memory per authenticated owner and target concept (or exact create payload). An explicit retry with the same operation, target, patch and optimistic version reuses the original `operationId`; a different operation on the same target is blocked while an outcome remains uncertain. A successful receipt or definitive validation, ownership or version conflict clears the pending command. Unknown server/network errors retain it. Read-only merge preview and flag-off behavior are unchanged.

Unit regressions simulate a server that committed an audited action but dropped both immediate responses, followed by an explicit retry for update, create, link and merge. They check exact envelope equality, one command receipt/action, changed-intent refusal while uncertain and a fresh ID after a confirmed completed edit. No SQL, capabilities or production deployment paths are changed.
