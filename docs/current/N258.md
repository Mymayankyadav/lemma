## N258 · Earlier first dictionary suggestions

The expanded tutor count model contains 407,745 history rows and 2,489,451 edges. The old loader allocated a typed-array view to compare each adjacent pair of histories and traversed the same edges separately for token validity, probability range and ordering. The worker now compares adjacent histories by offset and checks each row and its edges in place. Invalid row bounds, IDs, probabilities, backoffs and ordering are still rejected; the verified file, probability arrays, decoder, and candidate order are unchanged. This shortens work on a cold count-worker start, not neural graph decoding or the key paint path.

### Evidence

* In a shared-host test on the shipped 20 MiB pack, 15 parses had median times of 155.6 ms before and 63.1 ms after. In the smaller production LaTeX model the allocation regression measured 50,905 temporary history views before, zero after. This count is deterministic; no timing threshold was added.
* In a local Chromium build, the same user entry point (open tutor, type `def` before the worker was ready) was run in 24 fresh browser profiles: six ABBA blocks, 12 samples per build. Median worker creation to verified preload was **749.5 → 663.1 ms**; median surviving edit to its first count reply was **706.3 → 602.3 ms**. All 24 cases coalesced three edits into one request, used the same model fingerprint, and had zero failures or timeouts. Five of six blocks favored the new loader; one was slower. The test uses local assets, not a production network.
* An initial, non-interleaved seven-profile comparison went the other way under variable load (603 vs 1,013 ms median readiness). Do not use separate runs to predict an individual device’s latency. Neither comparison times key-to-display presentation or measures a physical phone/iPad. No neural pack or new model download is required for this change.
