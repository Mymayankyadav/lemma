## N92 — proposal revisions, citation sources and optional stale-target checks

The additive migration `20261116190000_proposal_versions.sql` retains the existing proposal status values and approval function signature while adding a semantic `payload_version`, `base_target_versions`, stable revision `group_id`, bounded `citations` array, `withdrawn_at` and an owner-composite `revised_from` FK. Each citation is the owner's immutable (source UUID, version, page label) assertion at the point it is supplied; newly stale, malformed or foreign citations fail atomically. Direct authenticated writes cannot forge the new metadata, even with caller-controlled session GUCs.

`withdraw_proposal` marks an active pending proposal withdrawn without destroying its history; `reopen_proposal` restores a rejected or withdrawn proposal only when an active successor does not supersede it; `revise_proposal` creates one owner-bound pending successor and withdraws the prior proposal in one journaled transaction. The existing `approve_proposal(uuid,jsonb)` remains compatible with legacy calls while accepting a reserved `expected_versions` field (resource to owner UUID to positive version) and automatically enforcing any explicit stored `base_target_versions`. Empty/omitted expectations preserve legacy approval behavior. Only owner-visible projects, notes and checkpoints can be targets. Existing card edit/plan approval effects and undo logs are unchanged.

PGlite regression: `tests/mcp/sql/proposal-versions.mjs` checks legacy approval, optional stale-version refusal, citations and owner isolation, lineage, withdrawal/reopen, authenticated metadata bypass refusal, audited writes, and complete registry columns. This is unapplied production SQL pending CI and independent review.
