## Bug #1202 — preserve card scheduling operationId on lost acknowledgement

The merged N104 SQL `card_schedule_command` stores exact receipts and safely returns one audit action per operationId, but its first live adapter created a fresh operationId for every button retry. An owner reschedule/reset that committed before its HTTP response was lost could therefore create a duplicate audit action, overwrite subsequent scheduling or make undo require multiple actions.

The live adapter now retains a single complete `card_schedule_command` envelope keyed by authenticated owner, note number and variant ordinal. An ambiguous network error leaves the exact envelope and operationId pending. A subsequent explicit retry of the same operation and due instant replays that ID; a changed intent on the same card is rejected until the prior one is resolved. A definitive success, conflict or server rejection clears the pending envelope so a new owner intent gets a new operationId. This is tab-local, with no new DB privileges, migrations or direct DML.

A regression uses an in-memory mock SQL receipt store, commits the first reschedule/reset, loses the HTTP acknowledgement, explicitly retries and verifies identical transmitted envelopes and exactly one stored journal action; a subsequent independent completed intent receives a new ID. The original N104 SQL/undo and v6 tests are unchanged.
