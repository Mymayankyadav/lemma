## N87 — MCP owner-editable settings coverage

Claimed for implementation against the capability registry. Planned scope is the MCP command functions and unit tests enumerating every owner-editable settings field. Validation must preserve unknown JSON section keys, optimistic versions and existing owner/source provenance. No production deployment or completeness claim at this stage.

Implemented registry-checked field allowlist (27 settings fields), strict scalar/N39 section validation, 21-weight FSRS-6 set or null/default reset, recursive unknown-key preservation, and an optional `expectedVersion` argument checked before queueing and in `mcp_commit` via CAS. A focused unit suite asserts exact owner-editable field inventory, typed invalid cases, deep JSON merge, forbidden metadata and stale versions. Merge is pending CI and independent MCP deploy review.

CI fix: the new unit suite now exercises a pure queued-settings-command constructor instead of importing the Deno MCP `control.ts` handler, whose `npm:` module specifiers cannot be resolved by Vitest. The actual handler calls that same tested constructor; the CAS predicate remains in `mcp_commit`.

### Review finding and safe fail-closed behaviour (bug #1197)

The capability registry currently calls `connector_last_client` owner-editable, but existing `public.mcp_commit` unconditionally resets it to the true `p_source` *after* every queued settings UPDATE. That makes the field impossible to change atomically within N87's allowed scope. Substituting a fabricated source would falsify audit provenance. N87 now rejects any requested edit of this field with an explicit error (including null) at the MCP settings batch builder; regression reads the deployed SQL contract and exercises the refusal. All other owner-editable fields remain supported. **N87 is not Done/Ready** until an Owner-authorized SQL/registry decision makes the field truly editable or reclassifies it as command-managed. Issue #1197 records exact reproduction.

N87 follow-up contract regression inspects the unchanged `mcp_commit` SQL's statement order (queued UPDATE then mandatory telemetry overwrite), confirms the actual `commitBatch` client source selection, and rejects mixed connector_last_client+other-field patches atomically.

A proposed direct PGlite test in tests/unit/mcp/settings-coverage.test.ts could not run because `@electric-sql/pglite` is only available to the separate SQL gate, not Vitest's unit-affected environment. The unapproved import was removed on the very next correction commit; no dependency was added. The unit test documents the exact SQL ordering but does **not** claim to execute or prove the persisted row. A SQL integration regression still needs a scope adjustment or an existing SQL-test owner. N87 remains Not Ready pending #1197.
