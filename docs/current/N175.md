## Atlas v3 migration and cutover preparation

Adds service-only `atlas_v2_migrate` (dry-run default), SHA-256 source diff, source-id-based deduplication, legacy tags and implied instructions, an explicit activation RPC and evidence-freeze trigger. Preparation does not set `atlas_migrated_at`. The manual rollback restores the prior save_progress function and removes the additive schema after post-cutover data is exported.

PGlite covers 146 source rows → 134 attempts, 12 merges, 24 unresolved and seven instruction events; no dry-run writes; repeat migration; owner write revokes; post-cutover typed writes; invalid-batch rollback; append-only attempts; frozen evidence; up → down → up.

No production dry run, activation, conversion approval or deployment occurred. Beta/EWMA removal, independent review, protected-test replacement and all production gates remain for the second pass. The activation RPC's release-report checks must be strengthened before production use.

Activation gate (chat-91357): `atlas_v2_activate` no longer trusts a self-reported `release_gates_passed` boolean. It takes a `release_report` and `atlas_check_release_report` compares every numeric gate of 07 (KF KL ≤ 0.040 / 0.050 and ≥ 40% below v2, calibration slope 0.85–1.15 and |intercept| ≤ 0.2, fatigue |z| ≤ 3, card KL not above default FSRS, duration log density ≥ −0.70 and coverage 0.75–0.85, attendance log loss ≤ 0.57, paired end-to-end > 0 and > 2 SE, resume ≤ 1,500 and cards ≤ 100 tokens) against its threshold: a missing gate is a failure, never a pass. It also requires app/MCP parity, no Beta imports, a diagnostics list in which a stream with 50 or more events is `ok` and one with fewer shows `insufficient data`, and — checked from the database itself — an approved conversion for every planning, active or paused project. `tests/mcp/sql/atlas-activation.mjs` covers every gate missing and failing, each other refusal and the successful activation. The report is still evidence supplied by the release run (the Python simulation gates run outside the database), so the production dry run, the Owner's approval of the diff and the independent review remain the real controls.

Token gates (chat-91357): `tokenGates` (`_shared/adaptive/tokens.ts`) computes the `resume_tokens_max` and `card_tokens_max` of the release report with the same 3-characters-per-token estimate the existing resume tests use; `research/sim/gates.py --tokens tokens.json` merges them, so every gate of the report now has a producer.

Independent review fixes (chat-91357): `atlas_check_release_report` requires every gate to be a JSON number (a string such as "NaN" or "-Infinity" is not a measurement), exactly the four diagnostic streams each with an integer `n` and a status, and an applied conversion for every active project (approved, decided, with a result, and its template checkpoints present), not just a row marked approved. The Owner approves the hash of a dry run taken after the conversions, because they add KCs and the diff covers concepts. `tests/mcp/sql/atlas-activation.mjs` covers each.
