## N170 Adaptive pace and Atlas memory: proficiency, items, node cards, worker core, calibration (Owner task)

PR 2 of 2 of the adaptive plan (spec Phases 4–6; plan `docs/spec/adaptive-learning-plan.md` §6). Builds on `docs/current/N169.md`. Flags `proficiency`, `items`, `atlas_memory` and `workers` live in `settings.flags` beside N169's, default off.

### What exists
- **Pure core** (`supabase/functions/_shared/adaptive/`): `proficiency` (Beta per concept class and level, every §9.2 weight, downward-only implications, repeat → familiar, forgetting through recheck R, predicted success, fast-track / scrutiny with 2-signal hysteresis, load-bearing-but-unexamined, node card), `items` (fingerprint, difficulty prior and Elo update, templates for every level, selection at p* .85 in [.70, .90], hold-outs never practised, never blocks, learning-profile draft and core levels), `digest`, `node` (card, digest, raw, trail, roll-up), `calibration` (Brier, buckets, scribe audit), `workers` (scribe validation, idempotent job runner with kill switch, daily token cap and one retry, candidate sets, alias proposals).
- **Migrations** `20261217*_n170_*.sql` (additive): `items`, `assumptions`, `concept_aliases` (undoable facts; `assumptions` and `concept_aliases` are MCP resources through one command), `worker_runs` (telemetry log, not a fact), `projects.learning_profile(_approved)`, and `save_progress` replaced so that, with `items` on, the question a tutor poses is registered once per fingerprint and linked to its evidence. Down script `supabase/rollback/N170.down.sql`, tested up → down → up.
- **MCP**: `get(what=node, id, depth=card|digest|raw, trail)` (within the spec's token budgets), `get(what=calibration)`, node cards in `resume`'s BRIEF (`atlas_memory`), the LBU line in FLAGS (`proficiency`), `learning_profile` edits, the instructions text.
- **From the N169 review**: queue refs carry the project slug when several projects are active; `edit … deferred_reason:"prune"` records `prune:approved`, so an approved prune can be restored later.

### Decisions
- **Concept classes** are the new `concept_aliases` table (a `same_as` link kind cannot be added to `concept_links` without changing its CHECK). Proficiency, rechecks and node cards pool per class; one class takes the nearer deadline and is core if any member is.
- **T5** is derived, not written: an assumption is withdrawn when it is revoked or when a later fail shows on that class and level, so undo stays exact.
- **Digests, node cards and proficiency are derived on read** (no `node_digests` table): cheap at this size, never stale, and nothing to keep in step with undo.
- Digest lines are built by code from evidence (outcome sequence and hints, with ids). An LLM-written line is not needed for provenance and is not used.
- A learning profile is drafted from source statistics by `draftProfile` and only takes effect once `learning_profile_approved` is true.

### Not built, and why
- **Workers do not run.** There is no LLM key and no decision yet on hosting (Edge Function + `pg_cron` was proposed). The scribe's validation, the job runner and the audit maths are tested with a mocked model; no Edge Function is added, so nothing is deployed that could be invoked. Wiring is a small follow-up once a key exists.
- Item difficulty `b` stays at its prior until a writer exists (it needs a whitelisted update path); selection and calibration use the prior.
- Mode (fast-track / scrutiny) is computed and tested but not yet surfaced in `resume`, and its 2-signal hysteresis is not persisted.
- The curator (exercise extraction), plan-probe → item conversion (the 48 kept prompts) and an `items` read/edit resource follow with the workers.
