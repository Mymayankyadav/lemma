## N188: Reused Edge worker hits its wall-clock limit during MCP smoke

The standalone MCP smoke runs [44549374643](https://github.com/Mymayankyadav/lemma/actions/runs/44549374643) and [44365186908](https://github.com/Mymayankyadav/lemma/actions/runs/44365186908) reused the same Supabase Edge worker for parts 3 and 4 in each run. The worker shut down with `WallClockTime` about 148–149 seconds after part 3 began. On Nov 19 every part-4 assertion passed, then shutdown occurred 36 ms after cleanup began. The client received an HTTP 546 response with zero steps, and the old formatter mislabeled part 4 as part 2. FIFO ticket acquisition and release succeeded. #1520 fixed a different Atlas plan-template assertion and did not shorten cumulative worker lifetime.

The project database is in Mumbai (`ap-south-1`), but the failed parts ran in `us-east-2` on Nov 18 and `us-east-1` on Nov 19 (Supabase project metadata and function request logs). Each database round trip incurred cross-region latency. The smoke now uses Supabase's [regional invocation header](https://supabase.com/docs/guides/functions/regional-invocation) for the four fixture requests from GitHub Actions to this project only. Local endpoints, other projects and normal MCP traffic keep their default routing. There are no new retries or sleeps; a real worker-limit failure is still a failure.

This change removes unnecessary serial owner-settings lookups only for commits that already specify their client; implicit fixture commits still use the owner's existing audit fallback. It also batches fixture page insertion, runs duplicate negative cases once across the suite, and overlaps independent verification reads. It preserves all 19 named checks, setup for each partition, cleanup attempts and verification, FIFO and existing timeouts. The formatter now preserves partition 3 and 4 and labels HTTP 546 without logging bodies or endpoint details.

The regression tests exercise hosted-only CI routing and cancellation, explicit and fallback audit provenance at the RPC boundary, and safe worker-limit diagnostics. After deployment, check the four selftest responses' `x-sb-edge-region` in the function logs, elapsed times, and final verified cleanup. Production timing and successful cleanup still need verification after independent review and deployment.
