## N232 Fast taps on the answer keyboard

Measured before the change (production build, Chromium at 393 × 873, 4× CPU throttle, 68 taps, Event Timing): median 64 ms and
p95 104 ms with an empty answer; median 168 ms and p95 264 ms with eight equation chips. Gboard expects a visible response within 20 ms.
The writing aid itself was about 1% of the cost; the rest was the page re-rendering and the editor being rebuilt on every tap.

What changed (written without running the repo's tests or a new measurement; the target p95 ≤ 50 ms with eight equations at 4×,
≤ 32 ms with an empty answer, is still to be confirmed):

- **The composer owns the text being typed** (`TutorComposer.tsx`). `cursor.text` is the live draft and is painted at once. The page
  above is told in a React transition (`startTransition(() => props.onChange(text))`), so a tap never waits for the transcript, header
  and keyboard icons to re-render. `emitted` remembers what the page has been told but may not have rendered yet, so a late render of an
  older value is not mistaken for an outside change; the effect that resets the history on an outside change now runs only when
  `props.value` itself changed and is not one of the emitted values. Send reads `history.current.present.text`, the freshest text.
- **The draft is saved when typing pauses** (`useDraft` in `DemoCheckpointTutor.tsx`): `change(value, true)` updates state at once and
  writes `sessionStorage` / `localStorage` after 600 ms, and on `pagehide`, when the page is hidden, when the tutor closes, and before
  `clearIfUnchanged`. `change(value)` without the flag still saves at once and returns whether it was saved (the queued-answer paths
  use it). A failed late write sets the "unsaved" flag.
- **The rich editor patches instead of rebuilding** (`TutorAnswerEditor.tsx`, `patchText`). When a change is a few characters inside
  one plain text node (no `$`, backslash or bracket in or next to it, no chip involved) that node's text is edited in place; chips and
  their KaTeX output are untouched. Any other change rebuilds as before. The staleness check reads the editor with `domText` and no
  longer computes selection offsets (`readTutorAnswer` cloned DOM ranges twice per change).
- **No `scrollHeight` read per tap for the plain answer box.** With `field-sizing: content` (CSS `@supports` in `tutor.css`) the browser
  sizes the box; the measuring code remains for browsers without it and for the grey-text mirror.

Not done: memoising `TutorKeyboard` (its callbacks are recreated each render) and moving suggestions to a worker (a lookup costs about
0.5 ms on a desktop; see N233). Follow-up: a Playwright perf spec using Event Timing at 4× throttling, listed with the timing checks.
