## N164.1 — reminders reach the phone over FCM while the app is closed (the delivery tick, `due` and `tutor`)

**Owner task** ("Ok let's setup fcm", scope "Timer and all notify kinds"; "Complete N164"). N164 was too large for one PR, so it is split in `NEXT.md`: this PR is N164.1, the hardest part end to end (the tick, its database operations, FCM delivery, the phone showing it, and no duplicate of the phone's own reminder); N164.2 maps the other six kinds; N164.3 adds action buttons, web-push parity, Settings and closes N160.10.

**What exists now.** `supabase/functions/notify/` already had the rules, copy, action tokens, web-push transport and `runNotifyTick`, with no route, no schedule and no database operations (N160.10). This adds:

- **Schedule.** `pg_cron` job `lemma-notify-tick` every five minutes (only if some owner has reminders on) calls `push_tick_kick()`, which posts `{"tick":true}` to the `push` Edge function with the same URL and vault secret as the timer outbox.
- **Tick.** `supabase/functions/push/tick.ts` runs the unchanged `runNotifyTick` with real adapters: `notify_enabled_owners` (reminders on and a phone or browser registered), `notify_candidates` + the owner's `settings.notify` → `noticePlan` (`push/notice.ts`) → the shared rules; only a decision to *send* is queued (`notify_queue`, one row per owner and key, so a key is never queued twice; a deferred or skipped key stays free); `notify_claim` marks due queued rows `sent` before sending (at most once; two overlapping ticks cannot send one row twice); `notify_record` marks a row nothing could deliver `failed` (`no_device`, `push_error`). Rows queued elsewhere (the connector's `test_notification`) are delivered by the same claim.
- **Message.** An FCM data message `{type:"notice", id, kind, title, body, url}` with a time to live by kind (6 h; digest 24 h; confirm 10 min) and a collapse key per row; a token FCM no longer knows is deleted.
- **Phone.** `PushMessage` parses it (only links into this app are accepted) and `LemmaMessagingService` shows it with `Reminders.post`, the code that shows the phone's own reminders (Review channel, private lock-screen text, a tap opens the screen).
- **No duplicate.** Once this phone's token is registered (`serverDelivers()`), `planReminders` no longer schedules the phone's own `due` reminder (block-start reminders stay local). Both deliver `due` only when `settings.notify.kinds.due` is `true`, so a switch in Settings governs both.
- **Kinds in this PR.** `due` (once a day at the study time, threshold, nothing studied yet, quiet hours, cap, spacing, live session) and `tutor` (fresh proposals once settled, or a saved session summary, two hours apart). Both use the existing rules and copy unchanged.

**Safe by default.** The owner's `settings.notify` is empty, so no owner is listed and nothing is sent until Reminders are switched on in Settings. With no vault secret or function secret the tick does nothing or answers 503, as for the timer.

**Tests.** `tests/unit/push/{notice,tick}.test.ts`, `tests/mcp/sql/notify-delivery.mjs` (owners, queue, claim, record, grants), `PushMessageTest` (notice parsing and link safety), `tests/unit/platform/push.test.ts` and `tests/unit/android/platform.test.ts` (no duplicate). The Android classes that touch Firebase were compiled by CI for N163; the changes here to `Reminders` and `LemmaMessagingService` are compiled by CI for the first time.
