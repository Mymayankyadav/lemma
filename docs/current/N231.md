## N231 Returning sessions and offline launch

Supabase already persisted the session. Every cold launch waited for a user lookup and the `bootstrap` RPC before mounting the requested route. An interrupted connection could leave an existing session behind the sign-in screen, while the service worker precached only the app assets.

Returning sessions now open the requested route from the existing device session while the SDK starts. Fresh OAuth callbacks still finish account setup before restoring their destination. After a successful setup, a receipt for the current account, session and time zone avoids running bootstrap again on each launch. Supabase refreshes the existing session when the device reconnects.

An online visit saves Today, Paths and recently loaded path and checkpoint details on that device. A cold offline launch restores those views from the existing owner-scoped snapshot and shows the saved time on Today. The snapshot is bounded to 2 MB, seven days and details for up to five paths. The app hydrates study records without loading the projected Settings data into live Settings. The token remains in Supabase’s storage. The cache strips credentials and live authorization scopes, checks the owner again after an asynchronous read, and drops the previous owner’s snapshot when the SDK reports an account change or sign-out.

This is shared by the PWA and the Android web bundle. The installed PWA needs an online visit to cache the app and study data. A device without a saved notebook can open the shell and fetch its data once connected.

Browser regressions exercise blocked setup, offline launch with an expired access token, reconnecting without Google sign-in, account switching and explicit sign-out. The Android web build and shell checks passed locally. Physical Android startup remains unverified.
