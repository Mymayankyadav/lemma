## N103 Account deletion (chat-82641#k8q3, WIP pending full owner-data audit)

v6 Settings shows a clear permanent-deletion warning and export-first link. It requires an explicit export acknowledgement and the exact typed phrase `DELETE MY ACCOUNT`; demo mode cannot invoke deletion, and the browser never supplies an owner ID. The request goes through the signed-in client's Edge Function and only signs out on the server's affirmative `{deleted:true}` reply.

The new service-role Edge Function requires a valid bearer token, verifies it through Auth, permits only two confirmation fields, calls a service-only begin-deletion RPC for precisely that token's user ID, and enumerates owner-ID-prefixed objects in every Storage bucket using bounded Storage list calls and Storage `remove` (never SQL object deletion). Only after cleanup does it call Auth Admin's hard delete, which cascades owner rows. Cleanup failures return an explicit retryable 503; they never pretend deletion succeeded or call Auth delete prematurely. The forward migration stores deletion-in-progress markers under RLS, revokes browser writes, and uses restrictive Storage INSERT/UPDATE policies plus an Auth-existence check to refuse uploads from in-progress accounts and JWTs that outlive deleted Auth rows. PGlite owner isolation/cascade checks and browser unit tests are included; a full audited owner-table/Storage test and independent security review are essential before Ready. The branch is intentionally WIP.

The export prompt opens the parent Settings export section using an explicit callback (not a same-route query string that the section selector ignores). A unit regression verifies the link is functional.

### Expired-lease continuation (chat-59731#z4q8)

The first full-migration SQL run failed when Auth hard deletion hit `actions_user_id_fkey`; the original Auth cascade did not remove every non-cascading audit row. The forward migration now adds a service-only owner-row cleanup function, callable only after a deletion marker exists. It walks all public owner-keyed base tables, deleting child rows before FK-blocked parents across bounded passes, verifies no owner rows remain and keeps the deletion marker until Auth removes it. Any unsatisfiable FK fails closed; it never drops constraints or changes another owner. The Edge Function calls this cleanup after Storage API removal and before Auth Admin hard deletion. The SQL regression checks service-only access, repeated safe cleanup, every owner-keyed table, the surviving deletion marker and the unaffected second owner. WIP until the full migration suite is green and independent review covers remaining non-user_id references and Storage cleanup behavior.

The first continuation's CI surfaced a separate FK dependency: `public.action_changes` has no `user_id` and references `public.actions` through `action_no`, so deleting only owner-keyed tables cannot remove the parent actions. The cleanup now deletes action details through an exact owner-scoped join before each pass over owner-keyed tables, retaining the other owner's audit details. The SQL regression seeds two owners' journal actions/details and checks the guard refuses deleting B without its own marker. This is bounded to the known non-owner-keyed audit table; no global FK disabling or cross-owner cleanup.

### Independent security review: concurrent browser writes

Reviewer chat-31415#v8r2 identified a second-tab race after owner cleanup: the deletion marker blocked Storage uploads but not an authenticated INSERT/UPDATE/DELETE in public owner tables; a late edit could recreate an action/audit reference and cause Auth deletion to fail. The additive migration now creates an account-deletion-aware SECURITY DEFINER trigger applied to every existing public base table with `user_id`, refusing authenticated writes by a marked owner before any journaling trigger fires. Its owner read-only checks and service-role cleanup are unchanged. A PGlite test verifies that A cannot INSERT a subject, UPDATE settings, or DELETE a note once marked, no new action is journaled, and unmarked B can still update settings. Fresh independent review and CI are required; no production deployment has occurred.

## Owner fix (bug #1212): deletion marker also blocks MCP service-role writes

`lemma_block_account_deletion_writes()` now refuses INSERT/UPDATE on owner-keyed tables for **every** role once the marker exists (the connector writes as `service_role` through `mcp_commit`, `mcp_command` and `mcp_seen`). Service-role DELETE stays open so `lemma_purge_account_rows` and Auth's cascade work; updates fired by foreign-key actions (trigger depth above 1) pass because their root statement was already checked. There is no session flag that lifts the guard. The `account-delete` function purges and retries Auth deletion up to three times to absorb a write that was in flight when the marker committed. Regression: `tests/mcp/sql/account-delete.mjs` runs a SECURITY DEFINER helper under `service_role` (the MCP execution context) against marked A (rejected) and unmarked B (allowed).

### Follow-up: audited MCP DELETE race

The account marker now denies DELETE as well as INSERT/UPDATE for ordinary marked-owner service-role commands. This matters because `log_change()` writes `actions` and `action_changes` after any DELETE; a late MCP deletion could recreate the FK blocker after cleanup. Only the service-only `lemma_purge_account_rows()` opens a row-locked, XID/backend-scoped cleanup window, inaccessible even to direct service-role table writes; it clears the window before returning. Auth FK cascades retain the nested-trigger exemption. PGlite rejects a marked-owner MCP-style DELETE, verifies no new audit entries, and still completes purge and Auth removal. Removed the accidentally tracked machine-local `node_modules` symlink from this PR.

The first SQL gate caught PostgreSQL's three-valued boolean logic: comparing an unset nullable cleanup XID to `txid_current()` produced `NULL`, so `NOT (false OR NULL)` silently missed a marked-owner DELETE. The guard now requires both marker window fields to be non-null before testing their values; the marked-owner MCP-style DELETE regression exercises the originally failing case.

The SQL regression now attaches the exact assertion site and expected/received values to otherwise anonymous `strictEqual` failures, so the CI feedback identifies the next failed invariant without relying on workflow logs.

The N103 SQL guard also limits the FK-cascade exception to a nested delete whose Auth owner row is already gone. Merely being triggered at depth above one cannot authorize an MCP delete against a still-existing, marked owner. The regression verifies the denied deletion does not erase the note, not just that some post-delete audit trigger raised an error.

The first N103 follow-up CI failures at `ACCOUNT_DELETE_CHECK_EB` were caused by a test-side RLS visibility mistake: the PGlite fixture defines a plain `service_role` without production's `BYPASSRLS`, so `SELECT notes` from that simulated role sees zero rows even if deletion was correctly refused. The regression still executes the DELETE as service_role but performs its postcondition count only after `RESET ROLE`, preserving the actual security check.

Follow-up SQL regression correction: the PGlite `service_role` fixture lacks BYPASSRLS, so a direct SELECT of the private marker while impersonating that role returns zero rows; check the cleared cleanup transaction only after resetting the fixture role. Purge and retry still execute as service_role, and the production marker remains inaccessible to MCP callers.
