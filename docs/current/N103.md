## N103 Account deletion (chat-82641#k8q3, WIP pending full owner-data audit)

v6 Settings shows a clear permanent-deletion warning and export-first link. It requires an explicit export acknowledgement and the exact typed phrase `DELETE MY ACCOUNT`; demo mode cannot invoke deletion, and the browser never supplies an owner ID. The request goes through the signed-in client's Edge Function and only signs out on the server's affirmative `{deleted:true}` reply.

The new service-role Edge Function requires a valid bearer token, verifies it through Auth, permits only two confirmation fields, calls a service-only begin-deletion RPC for precisely that token's user ID, and enumerates owner-ID-prefixed objects in every Storage bucket using bounded Storage list calls and Storage `remove` (never SQL object deletion). Only after cleanup does it call Auth Admin's hard delete, which cascades owner rows. Cleanup failures return an explicit retryable 503; they never pretend deletion succeeded or call Auth delete prematurely. The forward migration stores deletion-in-progress markers under RLS, revokes browser writes, and uses restrictive Storage INSERT/UPDATE policies plus an Auth-existence check to refuse uploads from in-progress accounts and JWTs that outlive deleted Auth rows. PGlite owner isolation/cascade checks and browser unit tests are included; a full audited owner-table/Storage test and independent security review are essential before Ready. The branch is intentionally WIP.

The export prompt opens the parent Settings export section using an explicit callback (not a same-route query string that the section selector ignores). A unit regression verifies the link is functional.
