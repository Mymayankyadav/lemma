# Local Tutor autocomplete on Snapdragon 4 Gen 4

Keep the current autocomplete in this release. A small local language model is plausible for reranking after a typing pause, but there is no measured improvement over Lemma’s existing candidates or verified keyboard latency and memory on the 6 GB target phone. An optional setting would be premature. Drawing recognition is a separate task and uses a 4.94 MB dedicated model. Its browser runtime, model and class metadata together are about 18.44 MB. [Shipped handwriting asset manifest](../../../public/models/tutor-symbols/detypify-0.3.0-lemma-v1/manifest.json)

Qualcomm confirms the **Snapdragon 4 Gen 4** name. Its product brief lists two performance cores up to 2.3 GHz, six efficiency cores up to 2 GHz and LPDDR5 support. The owner’s 6 GB is total device RAM shared with Android, the browser or WebView, and other apps. Peak application memory and Android’s memory-pressure behaviour matter more than whether the weights alone fit. [Qualcomm product brief](https://www.qualcomm.com/content/dam/qcomm-martech/dm-assets/documents/Snapdragon-4-Gen-4-Product-Brief.pdf) [Android low-memory guidance](https://developer.android.com/topic/performance/issues/lmk)

For scale, SmolLM2 360M’s 32 layers, five KV heads, and 64 values per head imply 10 MiB for a single 256-token FP16 key/value cache `(2 × 32 × 5 × 64 × 2 × 256 bytes)`. This is a calculation from the config. Runtime allocations, model conversion or upload staging and intermediate buffers can add to that separately. Measure cold load and steady state, with the drawing recognizer and an active Tutor chat present. ## Where it could run

- **Android native CPU** is the first path to test if a web experiment cannot meet the budget. Lemma’s APK already uses Capacitor, so this would require a native inference bridge. LiteRT-LM supports Android ARM64 CPU runs and llama.cpp documents an Android binding. Native GPU/NPU acceleration would require an exact device/backend/driver test. A Snapdragon platform name alone does not establish that the required operators work. [Lemma Android architecture](../../../android/README.md) [LiteRT-LM Android instructions](https://github.com/google-ai-edge/LiteRT-LM/blob/main/docs/getting-started/build-and-run.md) [llama.cpp Android guide](https://github.com/ggml-org/llama.cpp/blob/master/docs/android.md)
- **Browser CPU via WebAssembly** can use ONNX Runtime through Transformers.js in a worker. WASM multithreading depends on cross-origin isolation, so plan to measure the single-thread path. A larger ONNX model might support the API yet still miss the response or memory budget. [Transformers.js runtime and quantization](https://huggingface.co/docs/transformers.js/en/index) [ONNX Runtime performance guidance](https://onnxruntime.ai/docs/tutorials/web/performance-diagnosis.html)
- **Browser GPU** is a second path. Chrome 121 enabled WebGPU for supported Qualcomm and ARM GPUs on Android 12 or later. Probe adapter, features and model execution independently in Chrome and the APK’s Android System WebView. Preserve the built-in suggestions when the adapter fails or is unavailable. Chrome’s built-in Gemini Nano Prompt API currently excludes Android. Android’s native AICore is a separate, device-dependent path. [Chrome WebGPU announcement](https://developer.chrome.com/blog/new-in-webgpu-121) [Android WebView overview](https://developer.chrome.com/docs/webview) [Chrome Prompt API](https://developer.chrome.com/docs/ai/prompt-api) [Android AICore](https://developer.android.com/ai/gemini-nano)

Google’s published Qwen2.5 0.5B LiteRT-LM result is **251 prefill and 30 decode tokens/s on the Galaxy S24 Ultra CPU**. Google’s Gemma 270M launch also reports an internal battery result on Pixel 9 Pro. Neither measures this Snapdragon 4 Gen 4, keyboard latency, Android WebView or the Lemma workload. No latency or peak-memory figures have been measured for the target handset. [LiteRT-LM measurements](https://developers.google.com/edge/litert-lm/overview) [Gemma 270M launch and battery test](https://developers.googleblog.com/introducing-gemma-3-270m/)

## What would justify an optional setting

Today Lemma proposes vetted word prefixes and spelling choices, exact symbol aliases, and shorthand based on what the learner supplied. It validates the editor and selection revision at acceptance. The next inexpensive experiment is a tiny local ranking model over those same candidates. Use prefix frequency, typo cost and previous explicit selections before taking on the download and memory cost of a language model. Compare against the current ranking on held-out learner input, including names, mixed prose and TeX, and incomplete proof attempts. Track accepted suggestions, keystrokes saved, and unwanted substitutions. [Current completion engine](../../../src/features/tutor/input/completionEngine.ts) [Current policy](../../../src/features/tutor/input/completionPolicy.ts)

If a language model adds measurable value, first try the 135M browser export or the 270M native model. Score only candidate IDs already produced by the local policy. Use a small current-caret context and a bounded score request on a pause. The ordinary strip appears immediately, and a late ranking change is ignored once the draft, selection, IME state or account changes or the learner starts pressing a choice. The model has no route to emit a new candidate, complete a proof step or insert text automatically.

For the release decision, measure p50/p95 warm ranking time, first-load time and peak memory during normal and sustained use on the actual 6 GB phone. Use a 200 ms draft ranking deadline as an initial experiment target, with typing paint measured separately against the no-model baseline. Verify offline reuse, cancellation, main-thread responsiveness, app survival when backgrounded and restored, and the ability to remove the model assets. Only expose a default-off download setting if the quality gain compensates for those costs and the license and runtime work for the exact artifact. [INP guidance](https://web.dev/articles/optimize-inp) [Android memory constraints](https://developer.android.com/topic/performance/issues/lmk)
