## Run and claim procedure (source §8)

Create an append-only RUN comment in #455 with invocation nonce, actual saved-task ID if exposed, slot, full nominal/observed start instants, timing source, protocol generation and finish boundary. GitHub's returned comment ID is immutable `run_id=run:<id>`. Reconcile lost responses by nonce; do not duplicate uncertain mutations. Role switches retain run ID.

`finish_by ≤ min(nominal + 50 minutes, observed start + verified shorter runtime)`; stop new substantial work 10 minutes earlier. Unknown runtime does not establish a 50-minute capability: do read-only capability reconciliation until a safe budget is recorded. Late starts do not extend nominal boundaries. Checkpoint incrementally.

Before claim: fully read potentially live claims/releases, PR lease and holds. Post CLAIM with exact run, scope, full accepted revision, branch/head, dated start/expiry, generation. Read back, retaining an existing valid PR holder; otherwise earliest eligible conflicting claim-comment ID wins. Explicit overlap includes owned paths/integration scopes, not just matching task text. Bind readable PR Owner line to run and exact claim URL after winning. No same-role ownership inference. RELEASE identifies the exact claim ID and run; it cannot cancel another invocation or newer claim. Recheck before each consequential mutation/verdict/merge. Expiry is no proof a process died. These comments are cooperative coordination, not transactional locks.

## Dispatch and admission (source §§10–11)

:00 normally claims the hourly dispatcher scope, reconciles current main/plan/spec commits, intake watermark plus overlap, owner decisions, queues, active claims, dependencies and review capacity; daily perform a bounded full reconciliation. Advance a watermark only after successful complete reads. Publish one packet to #764 and append a publication record after immediate before/after readback. A body update is not compare-and-swap.

Use [packet.json](templates/packet.json). One ticket per slot :00/:15/:30/:45/:50, one primary action and one bounded fallback. Every ticket names the full nominal instance, latest admission, role/playbook, scope/revisions, owned paths or explicit read-only reason, authority/capability/reviewer links and continuity. Reference precise canonical sections rather than copying specs.

Normally packet admission ends next hour; latest ticket admission is nominal + five minutes or packet end, whichever is earlier. Admission is only for that nominal instance. Once admitted, a valid :50 claim may continue across packet expiry until its dated run deadline; expiry does not revoke it or admit the next run. Replacement packets preserve occupied claims. Future/expired/malformed packets grant no authority.

Ordinary workers read guard/control + ticket + assigned requirements/PR/handoff/playbook. Refresh scope-specific facts before actions. Fallback order: eligible appointment under reacquired claim; named bounded fallback; canonical Task Board next-up link; scope-limited triage. Budget initially five minutes/up to ten candidates, with complete evidence for any chosen action. Read errors stop affected pushes/CLEAR/merges. Recovery dispatcher needs its own won scope claim and no live competing dispatcher.

Prioritize P0 owner stop/security/main incidents, P1 shared blockers, P2 eligible release/verification, P3 review, P4 urgent intake/defects, P5 runnable features, P6 nonurgent planning/hygiene. Two healthy-cycle aging assigns an explicit action/blocker for ready merges and owner proposals. Review backlog >2 eligible PRs or one aged two cycles adds reviewer capacity before new features. Initial WIP: two assessment packages and one substantive writable PR per execution. Appointments persist two–four starts but never reserve an idle lease; two healthy starts without new evidence trigger investigation/reassignment.

## Mode behavior

| Mode | Authority |
| --- | --- |
| legacy / shadow | Retained legacy dispatcher and role playbooks; shadow suggestions grant no claims |
| cutover / rollback | Stop new affected writable claims; checkpoint/drain existing work under authorized control |
| active | Valid authorized chain, installed compatible digest, runtime ack and current-instance tickets; bounded fallback |
| missing/conflicting after adoption | Affected read-only containment; no inferred generation or authority |
