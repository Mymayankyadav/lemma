## Owner decisions (2026-11-05)

- **D1 Production deploys.** Agent items that add database objects or MCP tools (N10–N12 and later) may deploy to production on merge, provided they pass the additive-only migration guard in AGENTS.md "Safety".
- **D2 Release gates.** Full app/MCP parity (contract gates G1–G7) is required for the **new** v6 study resources before each is turned on. Parity for the existing columns listed in `Lemma_v6_Capability_Registry.json` is a separate later track and does **not** block v6.
- **D3 Chat as approval.** An explicit instruction in chat authorizes the same change as the app would, only for changes that can be undone, or that are shown as a preview and confirmed first. Anything that cannot be undone needs a preview.
- **D4 Sync.** Start with refresh-based sync: the app re-reads changed records on focus, on visibility change, or after its own writes. No live push or Realtime subscription yet.
- **D5 Undo for study tables (#861).** The item that makes study commands reversible (N11.3, or N11 if not split) may replace `public.undo_action(uuid,bigint,boolean)` compatibly, in one new migration, with the PR body line `Replaces function: undo_action (reviewer verified signature and behaviour)`. Allowed, and nothing else: (1) `create or replace` with the same signature, where the only change to the body is appending `'study_entries','study_intervals','calendar_blocks'` to both table lists (the lock loop and the "Unrecognized journal table" check); no `revoke` or re-`grant` (replacing keeps the existing privileges); (2) `lemma_log_change` triggers on those three tables using the existing `public.log_change()`, exactly as `20261029183249_action_log.sql` creates them for the other tables; (3) making those three tables' foreign keys `deferrable initially immediate`, as that migration did for all others, so undo can restore rows in any order. Tests (PGlite): undo restores a deleted calendar block; undo reverts a saved or updated study entry with its intervals; undo after a newer edit to the same row is refused; another owner's action is refused; the existing undo tests pass unchanged. The reviewer compares the new function body with the old one line by line and requests changes for any difference beyond the three table names.
- **D6 Connector owner for study writes (#912).** The connector reaches the database with the service-role key, so `auth.uid()` is null and `study_command` refuses it. Instead of widening `mcp_commit` or passing owner ids through arguments, N12 adds one new security-definer function `public.mcp_study_command(p_user, p_source, p)`, executable by `service_role` only. It checks that `p_user` has settings, sets transaction-local claims `{sub: p_user, role: authenticated}` and the `lemma.*` audit settings as `mcp_commit` does, then calls `study_command(p)`, so every owner check inside `study_command` still applies. `p_user` is the connector's verified owner (`Context.userId`), never tool input. Additive (a new function only), deployed on merge (D1), reviewed.
- **D7 Task commands, undo and connector wrapper (priority run 2026-11-06).** Tasks (`public.tasks`, N21) are written only through a new `public.task_command(p jsonb)`: security invoker, owner from `auth.uid()`, the same envelope, `command_receipts` retry/conflict rules and receipt shape as `public.study_command`, with `resource` `tasks` and `operation` `create`, `update` or `delete`. In the same single additive migration (N22) the item may: add `lemma_log_change` triggers on `public.tasks` with the existing `public.log_change()`; make the `tasks` foreign keys `deferrable initially immediate`; replace `public.undo_action(uuid,bigint,boolean)` compatibly exactly as D5 allows, where the only body change is appending `'tasks'` to both table lists (PR body line `Replaces function: undo_action (reviewer verified signature and behaviour)`); and create `public.mcp_task_command(p_user uuid, p_source text, p jsonb)`, identical in behaviour to D6's `mcp_study_command` except that it returns `public.task_command(p)`, executable by `service_role` only. Nothing else may change. It deploys on merge (D1) and is reviewed. The MCP `study` tool routes `resource: "tasks"` envelopes to `mcp_task_command` (N34).
- **D8 Remaining v6 records, registries and lanes (priority run 2026-11-06 evening).** (a) **Registries first (N36).** One additive migration adds `public.lemma_undo_tables(table_name text primary key)` seeded with exactly the current `undo_action` lists, and `public.lemma_command_resources(resource text primary key, command_fn text not null, mcp_ok boolean not null default true, schema jsonb not null)` seeded for `study_entries`, `study_intervals`, `calendar_blocks` (→ `study_command`) and `tasks` (→ `task_command`); it replaces `public.undo_action(uuid,bigint,boolean)` one last time so both allowlists read `lemma_undo_tables` (same signature and behaviour for every current table, reviewer verified line by line); and it adds `public.mcp_command(p_user uuid, p_source text, p jsonb)`, behaving exactly like D6's `mcp_study_command` but calling the function registered for `p->>'resource'` (unknown or `mcp_ok=false` resources are refused; the function name comes only from the registry, never from input), service_role only. After N36 no item replaces `undo_action` or adds an `mcp_<resource>_command` wrapper again: a new resource INSERTs its rows into both registries. (b) **New resource migrations** (presets, deadlines, practice topics/events, parked thoughts, goals, day plans, overlap acknowledgements, review runs, proposal drafts, study events, pending decisions, change feed) each use one additive migration: a table with `id`, `user_id`, `version`, `created_at`, `updated_at`, `source` (`app`/`mcp`/`worker`), owner-composite foreign keys `deferrable initially immediate`, owner RLS policy, `lemma_log_change` triggers, a `public.<resource>_command(p jsonb)` (security invoker, owner from `auth.uid()`, the envelope, `command_receipts` retry/conflict rules and receipt shape of `task_command`) and the two registry rows with a JSON field/operation schema. They deploy on merge (D1) and are reviewed. (c) **App modules** for each resource live in their own folder `src/data/<resource>/` (`contract.ts`, `demo.ts`, `live.ts`, `index.ts`, like `src/data/tasks/`); the live adapter calls `rpc('<resource>_command', envelope)` with the envelope of (b), so a module item runs in parallel with its migration and is tested with a mocked client. (d) **Study command changes** (saved-entry correction, block task links, timer modes, lease) replace `public.study_command` compatibly, one item at a time (N51, then N52), with the PR body line `Replaces function: study_command (reviewer verified signature and behaviour)`. (e) **Existing-table extensions** (versions/provenance, typed settings, evidence/review corrections, proposal versions, aliases, source revisions) add columns, triggers, tables and functions only; existing rows get values from column defaults or are read through `coalesce` (for example `coalesce(occurred_at, created_at)`), never by `UPDATE`. (f) **MCP items** all edit `supabase/functions/mcp/**`, so they form one chain through `Needs`. (g) **Turning v6 on** for everyone (the last item) waits for the Owner's explicit approval in the PR; physical-device checks are the Owner's release checks, not agent items. D4 (refresh-based sync) stays until the change-feed item ships.
