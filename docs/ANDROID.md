# Lemma on Android — build and test (ANDROID-01)

This is the Capacitor 8 native **debug** package for the existing Lemma web source. The generated Android project is committed in `android/`; bundled web assets in `android/app/src/main/assets/public/` are generated by `npm run android:sync` and must not be committed. No JavaScript or FSRS rewrite is involved.

## Prerequisites

- Node.js 22 with npm and the checked-in `package-lock.json`.
- JDK 21 (the CI workflow uses Eclipse Temurin 21).
- Android Studio 2025.2.1 or newer and an Android SDK, including API 36 for this scaffold's `compileSdkVersion` (install through Android Studio SDK Manager).
- Android USB debugging enabled for ADB installation, or a trusted device installer for APKs.

The official [Capacitor 8 Android setup](https://capacitorjs.com/docs/v8/getting-started/environment-setup) and the project's `android/variables.gradle` establish the Android toolchain requirements.

## Reproducible local build

From the repository root:

```sh
npm ci
npm run android:sync
cd android
./gradlew assembleDebug
```

The resulting APK is `android/app/build/outputs/apk/debug/app-debug.apk`. On Windows, run `gradlew.bat assembleDebug` instead. Do **not** run `npm run android:add` in a checkout that already contains `android/`: it is a one-time scaffold operation.

`npm run android:sync` rebuilds `dist/` and copies the current source into the native app; run it after every web source change before building. The checked-in application ID is `io.lemma.study`. The GitHub Actions workflow injects public `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` repository variables at build time. For local authenticated builds, set those public variables in your shell before `npm run android:sync`; never use a Supabase service-role/secret key in an APK.

## GitHub Actions and sideloading

The [Android workflow](../.github/workflows/android.yml) runs on pull requests and `main` pushes. It performs `npm ci`, syntax/plan/lane checks, Capacitor sync and `./gradlew assembleDebug`, then uploads the `lemma-android-debug` artifact. Open the workflow run in GitHub Actions and download/extract that artifact to get `app-debug.apk`.

Install with ADB:

```sh
adb devices
adb install android/app/build/outputs/apk/debug/app-debug.apk
```

For an APK downloaded from CI, replace the path with the extracted `app-debug.apk`. A debug APK uses a debug signing key, **not** a release key. Separate CI runners can produce debug APKs with different signing certificates, so a later APK might refuse an in-place update. Do not uninstall an existing Lemma installation without first safely exporting or synchronizing any unsaved/local-only study data. Release signing and in-place update delivery are future work, not established here.

## ANDROID-02 N4a — CI APK provenance preflight

Before the debug APK is uploaded, Android CI now runs `node test/android_apk_artifact.js android/app/build/outputs/apk/debug/app-debug.apk`. It checks the assembled APK's application ID `io.lemma.study`, launcher `io.lemma.study.MainActivity`, valid APK signing certificate, and **byte-for-byte equality** of the bundled `index.html`, `lemma.html`, service worker and web manifest against this build's `dist/` outputs. A stale/mismatched APK fails the workflow; no bypass or replacement of existing regression gates is introduced.

The same `lemma-android-debug` Actions artifact includes `android-apk-metadata.json` with the APK SHA-256, signing certificate SHA-256, version and bundled-asset hashes. Retain this file with the APK and compare its signing certificate with the **already installed** version before an in-place upgrade (D6). A successful signature verification does **not** mean two independently built debug APKs have matching signing keys; if keys differ, stop the upgrade rather than uninstalling or clearing study data. The metadata contains no study content, account credentials or private keys.

This is automated packaging provenance only. It does not establish launch, deep-link return, notification delivery, keyboard/safe areas, offline sync or update preservation on a real phone. Physical D1–D6 remain **NOT RUN** until recorded separately.

## ANDROID-02 N3a — consent-gated due reminder planning (policy only)

The native-only `NativeShell.planDueReminder({ optedIn, permission, localTime, earliestDueAt, now })` computes a **single deterministic, generic reminder intent**. It returns `null` unless the student has explicitly opted in, Android notification permission is already `granted`, a strict `HH:MM` local reminder time is configured, and both due/clock timestamps are valid. It never requests permission, reads cards, schedules an OS alarm or exposes this method to ordinary web browsers. It selects the next configured local time **at least one minute in the future and no earlier than the earliest due card**, including local date rollover; a one-year bound prevents very distant stale alarms. The intent contains only `Review cards`, `Your Lemma review is ready`, the `review` route and fixed ID `24001`—no private content, account identifiers or card titles.

**This is not a shipped notification feature.** N3b must pin and verify the compatible native Local Notifications plugin through the integration process, request permission only from an explicit B-owned consent action, persist the user's preference safely, cancel/replace fixed ID 24001 when opt-in, due state, account or schedule changes, and cancel on opt-out or permission revocation. Android notification tap routing must be scoped to the Review screen and verified; the planner's route is not itself a tap handler. Do not infer opt-in from existing review data. Automated `npm run test:android` checks consent/denial, invalid inputs, deterministic local timing, due-date rollover, stable replacement ID and web inertness. The D5 physical permission/notification/tap gate remains **NOT RUN**; Android build CI does not satisfy it.

## ANDROID-02 N3c — explicit permission and safe notification-tap bridge

The native shell now exposes three **native-only** interfaces: `NativeShell.checkDueReminderPermission()` (read-only; returns `granted`, `denied`, `prompt` or `unavailable`), `NativeShell.requestDueReminderPermission()` (may show the Android permission prompt, and must be invoked **only** from a student's explicit Settings button gesture), and `NativeShell.onDueReminderTap(callback)` (subscribe/unsubscribe to the validated `review` route). These APIs do not persist consent, schedule a notification or silently turn on reminders. A permission grant is **not** Lemma opt-in. Existing `reconcileDueReminder` still requires an independently persisted `optedIn: true` value and due/time data; no default automatic scheduling is added.

A passive `localNotificationActionPerformed` listener accepts only action `tap`, notification ID `24001` and `extra.route === 'review'`. It ignores other IDs, actions and routes, never forwards the notification payload, and queues at most one early tap until the UI explicitly subscribes. It does **not** call `App.go` before initialization; B must subscribe after the app shell is ready, check its own workspace state and navigate to Review. Duplicate delivery of the same event object is suppressed; separate genuine taps may still navigate. Plugin and subscriber exceptions are redacted. Web browsers expose none of these native interfaces.

**Remaining gates:** B-owned `ANDROID-02-N3-B1` Settings opt-in/time controls and safe persistence, user-gesture permission request, earliest-due state wiring and subscription to the Review route are still separate. No consent is inferred from card data or from the OS permission status. D5 physical Android permission/notification/tap acceptance is **NOT RUN**. `npm run test:android` covers mocked grant/denial/errors, no implicit permission request, early/invalid taps, subscriber isolation and web inertness; a passing debug APK is not proof of an OS-delivered notification.

## ANDROID-02 N3b — native reminder reconciliation (bridge only)

With `@capacitor/local-notifications@8.0.0` pinned, `NativeShell.reconcileDueReminder(settings)` is an explicit **native-only** API. It never calls `requestPermissions()`. It checks existing Android notification permission, applies N3a's strict opt-in/time/due policy, examines pending OS reminders and cancels/replaces only Lemma's fixed ID 24001. It preserves unrelated notification IDs and skips an unchanged reminder. Opt-out, invalid due/time or revoked permission cancel a previously pending Lemma reminder; absent plugin fails closed for an opted-in request. A low-importance `lemma-review-quiet` channel disables vibration and avoids high-priority interruption; no private card text or account data is included. Plugin errors are redacted. The schedule is only created when this API is explicitly called with valid opted-in settings, **not** automatically at launch or account sign-in.

**Still not complete:** there is no Settings opt-in/permission request UI or persistent consent yet (B-owned request `ANDROID-02-N3-B1`), no automatic due-state wiring from A's model, no tap-to-Review handler and no physical D5 evidence. The API does not itself obtain permission or imply consent. A future native tap slice must validate notification ID and route before navigating; B must request permission only on the student's explicit gesture. The Android 13 permission and Android 12+ scheduling behavior require device verification; CI uses a mocked plugin and a debug APK, not an observed OS notification. `npm run test:android` checks granted/denied, opt-out, stale cancellation, unchanged idempotency, rescheduling, unrelated ID preservation, plugin absence/error redaction and web inertness.

## ANDROID-02 N1b — trusted system-browser launch adapter

`NativeShell.openAuthBrowser(authorizeUrl)` is a native-only bridge to the Capacitor `Browser.open` plugin. It rejects every URL except the configured HTTPS Supabase origin's `/auth/v1/authorize` endpoint with one Google provider, the exact `io.lemma.study://auth-callback` redirect, and an S256 PKCE code challenge. Fragments, authorization codes, tokens, alternative domains, non-HTTPS URLs and duplicate required parameters fail closed. Browser/plugin errors are redacted, not logged with credentials. `NativeShell.closeAuthBrowser()` is best effort; browser lifecycle errors do not clear app data. The ordinary web build does not expose these APIs or invoke the native plugin.

**Important deployment gate:** Integration [PR #57](https://github.com/Mymayankyadav/lemma/pull/57) pinned `@capacitor/browser@8.0.0`; the bridge still returns a clear “update the Android app” error if the plugin is unavailable in an older installed APK, **not an in-WebView login**. Lane A must also wire `signInWithOAuth({skipBrowserRedirect:true})`, code exchange and pending-session/identity guards using the C-owned callback subscription. This C slice alone does **not** make Android Google sign-in functional. CI mocks the plugin interface; native device/browser interaction remains NOT RUN. No configuration changes, client tokens or production write are required for this slice.

## Android Back and resume (ANDROID-01 S2)

The pinned `@capacitor/app@8.0.0` matches Capacitor core. `npm run android:sync` links the native Android App plugin. The inline app code uses `window.Capacitor.registerPlugin('App')` only when running on the native platform and when the plugin is available; it registers nothing in ordinary browsers.

On the Android Back gesture or hardware button, Lemma closes an open sheet first, then returns secondary app screens to Home using the existing router (which does not push browser history). At Home, it calls `history.back()` if the native event reports prior history, otherwise `App.exitApp()`. The `resume` event is logged and, in N2a, dispatches a native-only synthetic `window.focus` event to reuse the existing guarded account-sync refresh listener. This does not invent an `online` event, force a write or activate an account/workspace. The listener coalesces repeated wakeups; existing identity and offline guards remain responsible.

`npm run test:android` checks these decisions with mocked bridge events. Physical-device Back, resume and offline-data verification are still pending. Never uninstall an app with unsaved local data as a workaround.


## ANDROID-02 N2b — Android soft-keyboard resize (native contract only)

The Capacitor MainActivity explicitly sets `android:windowSoftInputMode="adjustResize"` so Android is requested to shrink the WebView's available area when the soft keyboard opens, rather than panning over focused mathematical editors. This preserves the `singleTask` OAuth deep-link activity and native Back/resume handlers. `npm run test:android` checks the manifest contract and the Android CI builds a debug APK. This change does not edit CSS or alter saved data.

**Physical gate still NOT RUN:** on a tested APK, open the Cards search, edit a card's title/front/back and use an editor sheet in portrait and landscape. Show/hide the IME, check that the focused input, sheet actions and bottom controls remain reachable, and verify the keyboard does not obscure unsaved content. Repeat with gesture navigation and relevant safe-area insets. `adjustResize` is a request to Android, not proof of WebView/IME behavior on every OS version or edge-to-edge configuration; record exact device/OS/build and failures for a B-owned UI correction if needed. Do not clear app data during these checks.

## ANDROID-02 N2a — native foreground recovery wake (automated bridge only)

Android WebView may deliver Capacitor `App.resume` without the browser `focus` event used by `account_sync.js`. The native shell now dispatches a single synthetic `window.focus` per Capacitor resume to wake the existing debounced, identity-guarded sync scheduler. This reuses the same code path as ordinary web foreground recovery and does **not** fabricate a network-online state, bypass explicit account enrollment, replay unsaved edits outside the durable outbox or change Supabase data by itself. The native shell catches and redacts any WebView event-dispatch failure so foregrounding cannot be blocked by diagnostics.

`npm run test:android` verifies two native resume events, no fabricated online event, redacted dispatch failures, preserved Back/OAuth callbacks and inert ordinary web behavior. The real-device D1/D4 gates (foreground after process suspension, offline edit/restart/reconnect, exact-once server receipt) remain **NOT RUN** until a tested APK is installed on a phone. This slice does not implement Google PKCE code exchange; lane A owns that separate request.

## ANDROID-02 N1a — native OAuth return entry (web sign-in is unchanged)

The Android MainActivity now accepts only the custom-scheme route `io.lemma.study://auth-callback` via an `ACTION_VIEW` / `BROWSABLE` intent filter; normal launcher and Back behavior remain unchanged. `NativeShell` listens for native `App.appUrlOpen` and checks `App.getLaunchUrl()` for cold starts. It validates the scheme, exact host, path, absence of token fragments and nonambiguous `code`/**or** `error` query before forwarding the raw URL to an explicit `NativeShell.onAuthCallback(handler)` subscriber. It does not log the URL/code, create a cloud client, exchange a PKCE code, modify data or silently sign in.

This is a native **entry contract, not completed Google sign-in**. The native system-browser flow has its compatible `@capacitor/browser` dependency pinned by PR #57, but still requires lane A to wire `LemmaAccount.signInWithGoogle` to `skipBrowserRedirect:true`, launch the returned OAuth URL through `Browser.open`, and call Supabase `exchangeCodeForSession` after the scoped callback. Lane B retains presentation, consent/backup safeguards and error UI. Do not claim live OAuth until the callback and cancellation/invalid/duplicate-code tests pass in a coordinated PR. Do not add release credentials or include OAuth codes in diagnostic logs. Supabase's redirect allow-list must permit this exact callback; verify configuration securely without revealing private credentials.

`npm run test:android` exercises web inertness, rejection of unrelated/ambiguous/fragment URLs, a queued callback before its subscriber, duplicate warm/cold deliveries, cancellation/error callback and redacted exception handling with a mock Capacitor App plugin. The manifest/bridge tests are **mocked** and an Android debug CI build is **build evidence**, not a real device intent-return or successful OAuth exchange. The consolidated D1–D6 hardware checklist above remains NOT RUN. Existing devices receive native code only by a newly signed and installed APK; GitHub Pages does not update the bundled native app.
